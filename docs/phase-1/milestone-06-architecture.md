# P1-M6: Identity and credentials, technical approach

Status: Done

Implement the [approved first-run trust path](milestone-03-architecture.md#explicit-first-run-and-recovery-path) behind local owner commands and testable credential and proof components. M7 connects these components to the HTTP contract; M6 does not bind a listener or add an administrative endpoint. The owner settled the command, replacement, and live-revocation choices on 2026-10-08.

## Boundaries and interfaces

- `ApproveHubService` owns the persistent identity and credential store, proof signing, credential lookup, and local administrative operations. It exposes typed, non-HTTP results to M7: an Ed25519 signer, an authenticated requester ID and owner-assigned name, an authenticated decider role, credential-store revisions, and explicit uninitialized, corrupt, revoked, and storage-failure errors. No credential or file adapter enters `ApproveHubCore`.
- `ApproveHubCore` gains one domain operation to cancel every pending request for a revoked requester ID in one actor turn. It emits the normal terminal transitions and wakes waiters; decided and already terminal requests keep their outcome. The service adapter, never the GUI, invokes it after observing a revocation.
- `ApproveHubContract` holds the public pin and proof value types, strict unpadded Base64url encoding, canonical six-field proof bytes, and a one-use proof verifier that requires an independently installed pin. `ApproveHub` and future requester clients can reuse it. The verifier returns permission to proceed for one operation only after checking protocol, fixed listener, key ID, unused challenge, 60-second times, and signature in M3's order. M7 will wire that permission to bearer injection for **every** authenticated call, retry, and SSE reconnect.
- `ApproveHub` dispatches owner subcommands before starting SwiftUI and invokes the sibling `approve-hub-service` helper directly with `Process`, without a shell. The helper performs the local administrative operation and owns storage writes. M9 resolves the same helper inside the `.app` bundle and implements the already approved `approve-hub service` foreground launch. M6 tests both the helper command and owner-facing dispatch. Missing or incompatible helper binaries produce a clear error and make no storage change.
- Add focused identity tests to a service test target and proof tests to `ApproveHubContractTests`. Keep the existing targets and pinned package dependencies; CryptoKit, Security, and CommonCrypto are system frameworks.

## Durable state and secret handling

Store one versioned state document under the owner's Application Support `ApproveHub` directory. The directory is owner-only (`0700`), the state and lock files are owner-only (`0600`), and all opens reject symbolic links, wrong ownership, or broader permissions. The document contains the raw Ed25519 private-key representation, one decider verifier, requester records, and nonsecret credential audit metadata; derive the public key and key ID from the private key so stored copies cannot disagree. Each requester record has an opaque stable ID, validated owner-assigned display name, creation/revocation metadata, and at most one active verifier. Active names are unique under a documented, locale-independent Unicode normalization and case-folding comparison; preserve the entered spelling for display and reject unsafe invisible/control characters and surrounding whitespace. A revoked name may be reused for a new requester ID. The token itself and GUI decider token are never stored in this document. Requests and outcomes remain process-local as in M5.

Generate independent 32-byte CSPRNG secrets for requester and decider bearer tokens. Encode tokens with a version, role marker, opaque lookup ID, and unpadded Base64url secret so the service can select exactly one verifier. Hash each secret using PBKDF2-HMAC-SHA256 with an independent random salt, at least 600,000 iterations recorded with the hash format version, and a 32-byte derived value; compare derived bytes in constant time. Reject malformed encodings and role mismatches before lookup. Revocation removes the active verifier while retaining nonsecret audit metadata; `list` returns IDs, names, and status without verifiers. To replace a lost token, the owner revokes the old ID and adds a requester with a new ID and one-time token. The new identity cannot read or wait for requests owned by the old ID; those pending requests are cancelled.

Serialize all administrative changes with an advisory state lock. Read a complete, validated state before mutation, write a same-directory temporary file, flush it, atomically replace the document, and flush the directory. Each write advances a durable credential revision. A malformed, unknown-version, missing, or partially written state fails closed and is never silently reset. M7 reloads a coherent state snapshot for each authentication, so an add or revoke takes effect on the next authenticated request without restarting or discarding unrelated pending requests. A separate service-lifetime lock is held from startup through shutdown. Rotation requires its exclusive acquisition and refuses to run if the service still holds the lock or the fixed port is occupied. Secret data never enters command arguments, environment variables, general errors, or logs. The owner receives a newly generated requester token once on command stdout; setup and decider reset never print the decider token. Tests check captured output and the persisted bytes for token leakage.

Revocation commits under the exclusive state lock. M7 holds the corresponding shared lock while checking the requester's active status and performing a decision or delivering a wait result, so a decision cannot win after revocation commits and an in-flight wait cannot return approval under a revoked identity. The live service observes each store revision, cancels all still-pending requests for revoked IDs, and acknowledges the applied revision to the local CLI. `requester revoke` reports success only after that acknowledgement when a service is running. If acknowledgement times out, the CLI identifies the process holding the service-lifetime lock, verifies its executable path, owner UID, and process start time against the lease record, stops it, and waits for the lock to release; this drops all process-local pending requests and outcomes. It never intentionally signals an unknown or reused PID. If stopping the verified process fails, the command exits nonzero and reports that revocation committed but service shutdown could not be confirmed. A stopped service has no pending requests to cancel. M6 supplies the revision, bulk-cancel, and acknowledgement interfaces with focused tests; M7 wires and tests the cross-process watcher, fallback shutdown, and decision/wait race. No administrative HTTP endpoint is added.

## Setup, Keychain, and recovery

`setup` is explicit and idempotent when the complete initialized state already exists: it does not reveal or replace a credential. An explicit repeat invocation restores a missing GUI pin from the trusted local public key, without learning anything from the listener; the GUI can then verify proof and recover a missing decider credential through its local helper. On a fresh account setup creates the service signing key and decider secret, writes the GUI decider secret and public pin to distinct generic-password Keychain items, commits the initialized state, and prints the public pin plus grouped hexadecimal SHA-256 fingerprint. Setup creates no requester. The service's M7 startup gate will refuse to bind if the durable state is absent, incomplete, corrupt, or incompatible, and report a distinct uninitialized state for M8's Setup Required view.

Use a small explicit setup/rotation transaction marker so a process crash between Keychain and file writes is detectable. The service never serves from a pending transaction. The marker records the candidate state and a digest of its base state; recovery accepts only that base state or the already committed candidate, rejecting a stale marker before any write. A repeated local command can complete or safely roll back the transaction; it must not generate a silent second identity. A Keychain write failure leaves the state uninitialized or unchanged, reports an actionable error, and prints no credential. The Keychain items use account-local access and are read by the GUI adapter; M6 verifies the development CLI/helper round trip, and M9 verifies the ad-hoc bundled app's Keychain access. If the GUI copy of the decider secret is lost or rejected, a local helper operation revokes the old verifier, installs a new verifier and Keychain item, and reports no secret. M8 may invoke it only after successful pin verification. An identity mismatch never triggers reset.

`pin export` derives the versioned pin from the durable service key and prints the JSON pin document and grouped fingerprint, with no token or private key. The pin includes protocol version, `ed25519`, the raw 32-byte public key, and the SHA-256 key ID, all binary fields in unpadded Base64url. Rotation requires the service to be stopped, generates a fresh key, updates the GUI pin, and exports the new pin as a hard cutover; it never automatically updates a requester pin. A wrong or missing pin is a local verification failure with no bearer disclosure, not a reason to adopt the listener's key.

## Proof primitives

The signer accepts one decoded 32-byte challenge and an injected clock, constructs exactly the six fields in `IdentityProofPayload`, uses fixed RFC 3339 timestamps with an expiry at most 60 seconds after issue, and signs the RFC 8785-canonical UTF-8 bytes with the stored CryptoKit Ed25519 key. The verifier checks the pin's own key ID against its public bytes before use; rejects malformed, padded, or noncanonical encodings; checks the M3 fields and freshness in order; verifies the raw 64-byte signature; and consumes the challenge on either success or failure. A successful verification yields one authorization that must also be consumed within the signed time window before sending one bearer-bearing request. M7 owns HTTP challenge request/response parsing and `Origin` rejection.

## Owner command surface

The owner accepted these names on 2026-10-08:

| Command | Effect and output |
|---|---|
| `approve-hub setup` | Initialize once; print only pin and fingerprint. |
| `approve-hub requester add <name>` | Add a new requester ID with a unique active name; print ID and one-time token. After token loss, revoke the old ID first. |
| `approve-hub requester list` | Print IDs, names, and active/revoked status. |
| `approve-hub requester revoke <id>` | Revoke by opaque ID and cancel its pending requests; stop an unresponsive verified service if cancellation is unconfirmed. Print no token. |
| `approve-hub pin export` | Print current public pin and fingerprint. |
| `approve-hub identity rotate` | Replace service key and GUI pin; print replacement pin and restart/distribution guidance. |
| `approve-hub decider reset` | Revoke and replace local GUI credential without printing it. |

Use nonzero exit codes and short, secret-free diagnostics for invalid input, absent setup, Keychain failure, corrupt state, and failed lock acquisition. Document the exact commands and pin/token transfer guidance in the root README when the implementation lands. Do not add an agent adapter or expose any of these commands through HTTP.

4. Test signer/verifier together and verify that an unknown, wrong, or unverifiable service identity cannot trigger a bearer send in the M6 client seam. Hand M7 the typed signer, authentication lookup, proof-verification, revision observation, cancellation acknowledgement, verified-shutdown, and race-guard interfaces. Add no HTTP listener in M6.

## Owner decisions

The owner selected immediate add/revoke effect during a running service, service-stopped rotation, the command names above, a new requester ID on token replacement, cancellation of pending requests on revocation, unique active requester names, explicit `setup` repair of a missing GUI pin, and stopping a verified service if cancellation acknowledgement fails. M6 provides a coherent cross-process credential reload and holds the service-lifetime lock needed for M7 to enforce the rotation boundary. These decisions are recorded in the [phase changelog](changelog.md); no P1-M6 owner choice remains open.
