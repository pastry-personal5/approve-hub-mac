- 2026-10-07 — owner — Interview round 8, and P1-M1 closed. Starting the server: a human starts it either by launching the GUI or with a command. After a restart: the history and the owner's rules remain, and pending requests and session grants are dropped. The owner accepted all six research notes as the record of what was found, with the interview decisions overriding any conflicting recommendation, and they moved from Draft to Active. P1-M1 is `Done`. Still open for P1-M2 or later: the API server name, agent integration styles (deferred with the known agents), and exposure and the iOS minimum version (deferred with iOS).
- 2026-10-07 — owner — Interview round 7, remaining technical choices. App build: a script in the repo builds the `.app` from the SwiftPM output and signs it ad-hoc (the owner approved the script as the build step, so no third-party packaging tool and no Xcode project). Sandbox: no App Sandbox. Server crashes: not restarted automatically, a human starts it again. Request digests: every decision names a digest of the request, and the server rejects a mismatch. This is not what the research recommended, which suggested immutable requests with no digest until an iOS client exists, so P1-M2 must choose the canonical form that the digest is computed over, and the research note on security lists RFC 8785 as one option. The remaining open items are for P1-M2 or later: the API server name, whether the server can be started without the GUI, what survives a restart, agent integration styles, and exposure for iOS.
- 2026-10-07 — owner — Interview round 6, technical choices. Unreachable ApproveHub: "Always block (fail-closed)". When ApproveHub is down, not started, or a request times out, the requesting app blocks its action. ApproveHub cannot enforce this, so it is each requesting app's duty and the API will document it. This resolves the open item in [product-behavior.md](../product-behavior.md) and means any future agent shim must deny on failure. Dependencies: the owner approved Hummingbird with Swift OpenAPI Generator "(Recommended)" in principle. That covers the server, the generator as a SwiftPM build plugin, its runtime and transports, and their open-source dependencies. P1-M2 lists the exact packages, versions and licenses and confirms each is compatible with Apache-2.0. Nothing is added to `Package.swift` before the milestone that needs it. Local transport: a loopback port with a token, with the Origin header checked. Waiting: both a single submit-and-wait call and create-then-wait-in-steps.
- 2026-10-07 — owner — Interview round 5, and acceptance of the product scope. History: entries older than 90 days are removed automatically, and the owner can clear the history at any time. Alerting: a macOS notification with Approve and Deny, and a badge in the menu bar until the request is handled. The owner accepted the three statements derived from the research (outcomes, who may decide, out of scope for now), and asked for the text to be written now with open items marked. [product-behavior.md](../product-behavior.md) now holds the accepted product scope, and the proposal was archived as [research-product-scope.md](../archive/research-product-scope.md). One product question remains open and is listed there: what happens when ApproveHub is unreachable, deferred with agent integration. [ux-gui.md](../ux-gui.md) is still TBD, so the notification and badge details belong there.
- 2026-10-07 — owner — Interview round 4. Sensitivity rules match a requesting app or an action type, and only mark requests sensitive. An action type is named by the requesting app as free text, and ApproveHub matches the exact string. Each request carries a session id from the requesting app, and the app may send an explicit end call. A grant ends at that call or after 1 hour, whichever comes first. Start: "The server should be started manually by a human. Don't start at the login time." So there is no login item and requesting apps do not start the server. Round 3's launch logic still applies when a human launches the GUI. Whether a human can also start the server directly, without the GUI, is left to P1-M2. A request sent while no server is running now fails, which makes the deferred "unreachable" question more pressing for requesting apps.
- 2026-10-07 — owner — Interview round 3. Sensitive requests are never approved by a session grant, and a grant is never created from one. Hosting: the server runs in the background. When the GUI launches it finds out whether the server is running. If it is, the GUI is a true client of it. If it is not, launch logic starts the server in the background and also starts the GUI. How the server is started and kept running, and whether it also starts at login, are left to P1-M2. Distribution: only the owner's own Macs, so Developer ID signing and notarization are not needed to start. Minimum macOS: "macOS 26 or later". The skeleton's `Package.swift` has no platform entry yet and P1-M2 reconciles it with this floor.
- 2026-10-07 — owner — Interview round 2, product behavior. Expiry: a request waits 2 minutes by default, and a requesting app may ask for up to 10 minutes. Approving on the Mac: a click, with Touch ID required for sensitive requests. A request is sensitive if the owner's rules say so (the owner can mark requesting apps or action types) or if the requesting app flags it. Approval never edits a request. "Approve for the session" grants exist: a grant matches the same requesting app and action type, ends when the requesting app's session ends or after 1 hour, whichever comes first, and a request it approves is recorded in the history marked as approved by grant, with no notification. History: ApproveHub keeps decided requests with their full text, outcome and time until the owner clears them. Details and the questions this leaves open are in [research-product-scope.md](../archive/research-product-scope.md).
- 2026-10-07 — owner — Interview round 1, after the P1-M1 research drafts. Threat model: ApproveHub is a consent tool for cooperative agents, not a boundary against a malicious same-user process. Adapters: ApproveHub ships the API only, and custom apps bridge to agents. Known agents: "Defer known agents (Claude Code CLI, Codex CLI) to later phases", given as the answer to what happens when ApproveHub is unreachable, so that question is deferred with agent integration and no default was chosen. iOS: the first release is Mac only. These move from "Undecided" to "Decided" in AGENTS.md. Effect on the plans: P1-M2 treats agent bridging only as a constraint the API must not rule out, and does not design agent-specific integration.
